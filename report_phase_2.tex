% PROJECT ABSTRACT
\sectiontitle{Project Abstract}

\vspace{0.12cm}

\answerbox{4.00cm}{BudgetBee is a website for keeping everyday money matters in one place.It helps users record expenses, check monthly
budgets, keep track of bills, and follow savings goals.The dashboard shows income and spending totals, along with an estimate of how much money is left to spend.Users can add and manage transactions, group expenses by category, and see how close they are to a budget limit. Separate sections cover bills and EMIs, savings goals, and a What-if tool for estimating how a planned expense may affect the budget.The site also provides spending indicators and lets users export transaction records as a CSV file.The current version is a frontend prototype made with HTML, CSS, and JavaScript.It stores data in the browser, rather than in an online account.}

\vspace{1.70cm}

% UPDATED PROJECT APPROACH
\sectiontitle{Updated Project Approach and Architecture}

\vspace{0.25cm}

\answerbox{4.50cm}{We have built the current version as a single-page website, with navigation tabs for its main sections. HTML provides the
structure, CSS controls the layout and visual design, and JavaScript handles interactive features such as transaction
updates, budget calculations, bill status, savings progress, and CSV export. The browser's localStorage API keeps data
available when the page is reopened in the same browser. The dashboard uses transaction records to calculate spending
totals and budget usage. The supplied version does not have a separate server, remote database, or frontend-to-backend
communication. Our next step is to test the existing features with sample data, compare financial calculations with manual
results, and check the layout on different screen sizes. Backend and database support could be considered later if they are
required by the project scope.}

% CHALLENGES
\sectiontitle{Challenges/Roadblocks}

\vspace{0.18cm}

\answerbox{9.35cm}{One of the main challenges in developing BudgetBee has been maintaining consistency between the different sections of the website. When a transaction is added or deleted, the dashboard, category-wise spending information, and budget alerts need to reflect the updated values. This requires careful handling of financial calculations and application data.

Another challenge is managing financial records using browser storage. The current application uses localStorage, which is suitable for a frontend prototype but does not provide centralised storage or separate accounts for multiple users. Data availability is also tied to the browser where it was saved.

Making financial information easy to understand has also been an important consideration. Budget indicators, spending summaries, progress bars, and alerts have been included to help users interpret their financial position without needing advanced financial knowledge.

The application contains several interactive features, so these need to be tested with different inputs to identify possible calculation errors or unexpected behaviour. Particular attention is required when checking transaction dates, budget limits, bill payments, savings targets, and CSV export.

To address these challenges, we plan to test each feature separately, compare calculated results against manually verified values, and correct any issues found during testing. We will also check the interface on different screen sizes and improve input validation wherever necessary.

If the final project scope requires additional functionality, backend integration and database support can be considered as future improvements. These changes would help extend the current prototype beyond its existing browser-based implementation.}
